# CreditLens 프로젝트 계획서

> 대출 신청·외부 신용·과거 상환 데이터를 활용해 상환곤란 위험을 예측하고, 금융기관의 우선심사를 지원하는 교육용 AI 프로젝트

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 팀명 | CreditLens Lab |
| 프로젝트명 | CreditLens - 대출 상환위험 분석 및 우선심사 지원 서비스 |
| 프로젝트 유형 | 개인 프로젝트 |
| 개발 기간 | 4주 |
| 저장소 | `CreditLens` |
| 개발 환경 | WSL2 Ubuntu, VS Code, Google Colab, Python |
| 현재 상태 | Stage 0 초기 환경 구성 완료 |
| 다음 단계 | Stage 1 데이터 확보 및 무결성 확인 |

### 한 줄 정의

대출 신청정보와 과거 신용·납부 이력을 고객 단위로 결합하여 상환곤란 확률을 예측하고, 위험 가능성이 높은 고객을 우선 검토하도록 돕는 서비스다.

## 2. 문제 정의와 프로젝트 범위

### 해결하려는 문제

금융기관이 모든 대출 신청자를 동일한 깊이로 심사하려면 많은 시간과 인력이 필요하다. 또한 상환곤란 고객은 전체 고객 중 소수이므로 단순 규칙이나 정확도만으로는 위험고객을 효과적으로 찾기 어렵다.

### 머신러닝의 역할

과거 대출 신청정보, 외부 신용거래, 납부기록을 학습하여 신규 고객의 상환곤란 확률을 예측하고, 위험 가능성이 높은 고객을 우선심사 대상으로 분류한다.

### 포함 범위

- 고객별 상환곤란 확률 예측
- 저위험·중위험·고위험 등급 제공
- 고객별 주요 위험요인 설명
- 심사 자원을 고려한 우선심사 대상 제안
- 데이터 버전과 모델별 성능 비교
- FastAPI 예측 API와 Streamlit 분석 화면 구현

### 제외 범위

- 대출 자동 승인·거절 또는 실제 신용 의사결정
- 실제 개인신용정보의 수집·처리
- 실서비스 수준의 보안·규제 인증 및 운영 배포
- 핵심 Stage 완료 전 GRU·LSTM 등 시계열 확장 모델 구현

### 서비스 원칙

CreditLens는 심사자의 판단을 보조하는 교육용 프로토타입이다. 모델 결과만으로 대출을 승인하거나 거절하지 않으며, 예측확률과 위험등급은 검토 순서를 정하기 위한 참고 정보로만 사용한다.

## 3. 목표와 최종 산출물

### 사용자에게 제공할 결과

- 상환곤란 예측확률
- 저위험·중위험·고위험 등급
- 고객별 주요 위험요인
- 우선심사 필요 여부
- 모델별 성능 비교 결과

- V1·V2·V3 고객 단위 분석 데이터셋(로컬 보관, Git 제외)
- 기준 모델과 후보 모델 비교 보고서
- 최종 전처리 파이프라인과 학습 모델(로컬 보관, Git 제외)

- 테스트, 데이터 사전, 모델 카드, README 및 결과 보고서

### 성공 기준

- 모든 모델을 동일한 분할과 평가 함수로 비교한다.
- Accuracy 대신 PR-AUC, Recall, KS, Lift 등 불균형 데이터에 적합한 지표를 함께 사용한다.
- 전처리와 임계값은 학습·검증 데이터에서만 결정하고 테스트 데이터는 최종 평가 전까지 봉인한다.
- 데이터 구축부터 API 예측까지 동일한 피처 정의를 재사용한다.
- 성능 수치와 분석 결과는 실제 실행 결과만 기록한다.
- 원본·중간·가공 금융 데이터와 학습 모델 파일, 인증정보가 Git에 포함되지 않는다.

구체적인 목표 성능은 데이터를 확인하기 전에 임의로 정하지 않는다. Stage 4 기준 모델 결과를 측정한 뒤 개선 목표와 최종 선정 기준을 확정한다.

## 4. 데이터 계획

### 데이터 소스

- 데이터셋: Kaggle Home Credit Default Risk
- 주소: <https://www.kaggle.com/competitions/home-credit-default-risk/data>
- 예측 대상: `TARGET`
  - `TARGET = 0`: 정상 상환 고객
  - `TARGET = 1`: 상환에 어려움이 있었던 고객

### 핵심 사용 파일

| 파일 | 예상 규모 | 주요 내용 | 역할 |
|---|---:|---|---|
| `application_train.csv` | 약 30만 행, 122개 컬럼 | 소득, 대출금액, 연간 상환액, 직업, 가족, 주거, 외부 신용평가값, `TARGET` | 현재 대출 신청정보와 정답 |
| `bureau.csv` | 약 171만 행, 17개 컬럼 | 타 금융기관 과거 대출, 대출잔액, 연체금액 | 외부 신용이력 |
| `installments_payments.csv` | 약 1,360만 행, 8개 컬럼 | 납부 예정일·실제 납부일, 예정금액·실제 납부금액 | 과거 상환 행동 |

파일 규모는 데이터 확보 후 실제 값으로 다시 기록한다.

### 고객 단위 데이터 구축 원칙

`bureau.csv`와 `installments_payments.csv`는 한 고객이 여러 행을 가진다. 원본 테이블을 직접 이어 붙이지 않고 `SK_ID_CURR` 기준으로 고객별 통계를 먼저 집계한 뒤 신청정보와 결합한다.

```text
고객 ID | 신청정보 | 외부 신용이력 요약 | 납부행동 요약 | TARGET
```

### 주요 파생변수 후보

- 소득 대비 대출금액
- 소득 대비 연간 상환액
- 대출금액 대비 상품가격
- 나이 대비 재직기간
- 과거 신용거래 건수와 진행 중인 외부 대출 수
- 총 외부 대출잔액과 최대 연체금액
- 전체·지연·미납 횟수와 비율
- 평균·최대 지연일
- 미납금액과 예정금액 대비 실제 납부 비율

피처는 Stage 3에서 정의서와 함께 확정하며, 예측 시점 이후 정보가 포함되지 않는지 각각 검토한다.

### 데이터 버전

| 버전 | 사용 데이터 | 목적 |
|---|---|---|
| V1 | 대출 신청정보 | 기준 성능 측정 |
| V2 | V1 + 외부 신용이력 | 외부 신용정보의 추가 가치 측정 |
| V3 | V2 + 납부기록 | 실제 상환 행동의 추가 가치 측정 |

### 데이터 관리 원칙

- Kaggle 약관을 확인하고 데이터 원본은 `data/raw/`에 보관한다.
- 내려받은 원본 파일은 수정하지 않는다. 정제 중간 결과는 `data/interim/`, 최종 분석 데이터는 `data/processed/`에 저장한다.
- `data/` 아래의 금융 데이터는 단계와 용량에 관계없이 GitHub에 올리지 않는다.
- 원본 대신 다운로드 절차, 스키마, 데이터 사전과 재현 가능한 구축 코드를 기록한다.
- 실제 개인신용정보가 아닌 익명화된 공개 데이터만 사용한다.
- `.env`, `kaggle.json` 등 인증정보는 Git에서 제외한다.

### Stage 0. 프로젝트 초기 환경 구성

**목표**

데이터나 모델링을 시작하기 전에 재현 가능하고 안전한 저장소 뼈대를 만든다.

**구현 단계**

1. 프로젝트 계획서를 `docs/Project_Plan.md`로 정리한다.
2. `README.md`, Python용 `.gitignore`, `requirements.txt`를 만든다.
3. `data/raw`, `data/interim`, `data/processed`, `models`, `notebooks`, `reports/figures`, `src/creditlens`, `tests` 기본 폴더를 만든다.
4. 가상환경 생성, 의존성 설치, 데이터 배치 방법을 README에 문서화한다.
5. 금융 데이터, 모델 파일, 환경변수와 Kaggle 인증정보가 Git에서 제외되는지 확인한다.

**산출물**

- 프로젝트 기준 계획서와 README
- 초기 의존성 목록
- 빈 기본 디렉터리와 Python 패키지 뼈대
- 데이터·모델·비밀정보 보호용 `.gitignore`

**완료 조건**

- `git check-ignore`로 `data/raw`, `data/interim`, `data/processed`의 샘플 파일과 `models`의 샘플 모델 경로가 제외된다.
- Git 상태에 실제 금융 데이터나 모델 파일이 없다.
- 데이터 처리·모델 학습·API 구현 코드는 아직 없다.

### Stage 1. 데이터 확보 및 무결성 확인

**목표**

필요한 원본을 안전하게 확보하고, 모델링 전에 구조와 품질을 이해한다.

**구현 단계**

1. Kaggle 대회 약관에 동의하고 다운로드 절차를 문서화한다.
2. 핵심 CSV를 `data/raw/`에 내려받고 원본 불변 원칙을 적용한다.
3. 파일 존재 여부, 크기, 행·열 수, 컬럼명과 자료형을 확인한다.
4. 기본키·외래키, 중복, 결측치, 무한값과 범위 이상을 점검한다.
5. `TARGET` 분포와 클래스 불균형 정도를 확인한다.
6. 데이터 사전 초안과 자동 검증 보고서를 만든다.

**산출물**

- 데이터 다운로드 안내
- 데이터 사전 초안
- 데이터 무결성 검증 코드와 보고서

**완료 조건**

- 세 핵심 테이블의 스키마와 키 관계를 설명할 수 있다.
- 치명적인 누락·중복·타깃 이상 여부가 기록되어 있다.
- 원본 데이터가 Git 추적 대상에 포함되지 않는다.

### Stage 2. 분할 전략·EDA·전처리 설계

**목표**

데이터 누수를 막는 검증 구조와 일관된 전처리 원칙을 확정한다.

**구현 단계**

1. 고정 random seed와 층화 학습·검증·테스트 분할을 정의한다.
2. 테스트 세트는 최종 Stage 6 평가 전까지 봉인한다.
3. 수치형·범주형 변수 분포, 결측률, 이상치와 상관관계를 분석한다.
4. 결측치 제거·대치·`Unknown` 처리 기준을 변수 의미별로 정한다.
5. 범주 인코딩, 스케일링과 이상치 처리 정책을 정한다.
6. 전처리기는 학습 데이터에만 `fit`하도록 파이프라인을 설계한다.
7. 예측 시점 이후 정보와 타깃 대리변수 등 누수 후보를 검토한다.

**산출물**

- EDA 노트북과 핵심 시각화
- 데이터 분할 명세
- 전처리·누수 점검 명세

**완료 조건**

- 동일 seed로 같은 고객 분할을 재현할 수 있다.
- 전처리 결정의 근거와 누수 제외 변수가 문서화되어 있다.
- 테스트 데이터가 탐색·튜닝 과정에 사용되지 않는다.

### Stage 3. 고객 단위 피처와 V1·V2·V3 구축

**목표**

일대다 이력을 고객당 한 행으로 집계하고 세 데이터 버전을 재현 가능하게 만든다.

**구현 단계**

1. 신청정보 정제와 V1 피처 생성을 구현한다.
2. `bureau.csv`를 `SK_ID_CURR` 기준으로 집계해 V2를 만든다.
3. `installments_payments.csv`를 고객 기준으로 집계해 V3를 만든다.
4. 비율·건수·금액·지연 관련 금융 파생변수를 계산한다.
5. 고객 수, 키 유일성, 조인 후 행 수와 타깃 보존을 검증한다.
6. 피처명, 산식, 원천 테이블, 결측 의미를 피처 사전에 기록한다.
7. 중간·최종 결과를 Parquet으로 로컬 저장한다.

**산출물**

- 재현 가능한 피처 생성 코드
- V1·V2·V3 Parquet 파일(로컬 전용)
- 피처 사전과 집계 테스트

**완료 조건**

- 각 버전이 고객당 한 행이며 고객 수와 타깃이 의도대로 유지된다.
- 동일 입력과 설정으로 같은 결과를 다시 생성할 수 있다.
- 중간·가공 데이터가 Git에서 제외된다.

### Stage 4. 기준 모델과 공통 평가 체계 구축

**목표**

향후 모델을 공정하게 비교할 기준선과 평가 함수를 만든다.

**구현 단계**

1. Dummy Classifier로 최저 기준을 측정한다.
2. V1 데이터로 Logistic Regression 기준 모델을 학습한다.
3. 공통 평가 함수에 ROC-AUC, PR-AUC, KS, Gini와 Top 10% 지표를 구현한다.
4. Confusion Matrix와 ROC·PR·Calibration Curve를 생성한다.
5. 모델, 데이터 버전, seed, 전처리 설정과 실행시간을 기록한다.
6. 우선심사 임계값은 검증 데이터에서만 탐색한다.

**산출물**

- 기준 모델 학습 파이프라인
- 공통 평가 모듈과 기준 성능 보고서
- 재현 가능한 실험 설정

**완료 조건**

- 동일 분할에서 기준 모델 지표를 재현할 수 있다.
- 지표 단위 테스트와 수기 검산 결과가 일치한다.
- 이후 모델이 같은 평가 인터페이스를 사용할 수 있다.

### Stage 5. 후보 모델 비교·튜닝·확률 보정

**목표**

데이터 추가 가치와 모델 복잡도의 효과를 공정하게 비교한다.

**구현 단계**

1. Random Forest와 LightGBM을 동일 분할에서 학습한다.
2. LightGBM으로 V1·V2·V3 성능을 비교한다.
3. class weight 등 불균형 대응 방식을 검증 데이터에서 비교한다.
4. 제한된 탐색 공간으로 하이퍼파라미터를 조정한다.
5. 필요하면 검증 데이터 내 별도 calibration 구조로 확률을 보정한다.
6. 핵심 ML 실험 후 TensorFlow MLP를 동일 조건에서 비교한다.
7. 성능, 학습·추론시간, 모델 크기와 설명 가능성을 함께 비교한다.

**산출물**

- 모델·데이터 버전별 비교표
- 튜닝과 calibration 실험 기록
- 최종 모델 후보와 선정 근거

**완료 조건**

- 모든 후보가 같은 분할과 지표로 평가된다.
- 데이터 버전 추가 효과와 모델 복잡도 효과를 구분해 설명할 수 있다.
- 테스트 세트는 아직 최종 선택에 사용되지 않는다.

### Stage 6. 해석·위험정책·최종 검증

**목표**

최종 모델을 고정하고, 사람이 이해할 수 있는 위험 근거와 운영 기준을 만든다.

**구현 단계**

1. 검증 결과에 따라 최종 전처리와 모델을 고정한다.
2. SHAP으로 전역 중요도와 고객별 주요 위험요인을 계산한다.
3. 심사 가능 인원과 검증 성능을 기준으로 우선심사 임계값을 정한다.
4. 저·중·고위험 등급 경계와 각 구간의 실제 상환곤란 비율을 확인한다.
5. 금융이력 부족자와 주요 하위그룹의 성능·오류 차이를 점검한다.
6. 고정된 모델로 봉인한 테스트 세트를 한 번 평가한다.
7. 제한사항, 오용 위험과 사람의 최종판단 원칙을 모델 카드에 기록한다.

**산출물**

- 최종 성능표와 테스트 결과
- SHAP 설명 결과
- 위험등급·우선심사 정책
- 모델 카드 초안

**완료 조건**

- 최종 선택과 임계값의 근거가 검증 데이터 결과로 설명된다.
- 테스트 결과를 본 뒤 모델이나 임계값을 다시 조정하지 않는다.
- 모델의 한계와 사용 금지 범위가 문서화되어 있다.

### Stage 7. FastAPI·Streamlit 서비스 구현

**목표**

검증된 전처리와 모델을 일관된 API·화면으로 제공한다.

**구현 단계**

1. 전처리와 모델을 하나의 재현 가능한 추론 파이프라인으로 저장한다.
2. Pydantic 입력·출력 스키마와 유효성 검사를 정의한다.
3. FastAPI에 상태 확인과 예측 엔드포인트를 구현한다.
4. Streamlit에 데이터 분석, 모델 비교, 고객 위험 분석 화면을 구현한다.
5. 예측확률, 위험등급, 주요 위험요인과 우선심사 여부를 표시한다.
6. 누락 입력, 범위 오류, 모델 부재와 내부 오류를 안전하게 처리한다.
7. API·추론 통합 테스트와 Swagger 문서를 확인한다.

**산출물**

- FastAPI 예측 API
- Streamlit 대시보드
- 입력 스키마와 API 테스트

**완료 조건**

- 같은 입력에 API와 화면이 같은 결과를 제공한다.
- 자동 승인·거절 기능 없이 심사 보조 정보만 제공한다.
- 학습 모델 파일은 Git에 포함되지 않는다.

### Stage 8. 품질 검증·문서화·발표 준비

**목표**

다른 환경에서 재현 가능한 결과물과 시연 자료를 완성한다.

**구현 단계**

1. 핵심 전처리·피처·평가·API 테스트를 실행한다.
2. 빈 환경에서 설치와 주요 실행 절차를 검증한다.
3. 1만 건 추론시간, 모델 크기와 오류 처리를 점검한다.
4. README에 실제 사용법, 구조, 성능표와 제한사항을 갱신한다.
5. 데이터 사전, 데이터 카드, 모델 카드와 결과 보고서를 완성한다.
6. 서비스 시연 시나리오와 발표자료를 만든다.
7. 필요하면 마지막에 Docker 실행환경을 추가한다.

**산출물**

- 테스트 결과와 재현 절차
- 완성된 문서와 결과 보고서
- 서비스 시연 및 발표자료
- 선택 사항인 Docker 환경

**완료 조건**

- README만으로 설치와 시연 절차를 따라갈 수 있다.
- 성능표의 모든 수치가 저장된 실험 결과와 일치한다.
- Git 추적 파일에 데이터, 모델, 비밀정보가 없다.

## 8. 예상 이슈와 대응

| 이슈 | 대응 |
|---|---|
| 클래스 불균형 | Accuracy에 의존하지 않고 PR-AUC, Recall, KS, Lift를 함께 평가한다. |
| 결측치 | 결측률과 업무적 의미에 따라 제거·대치·`Unknown` 처리를 구분한다. |
| 일대다 관계 | 고객 단위로 먼저 집계한 뒤 신청정보와 결합한다. |
| 데이터 누수 | 분할 후 학습 데이터에만 전처리를 적합하고 예측 시점 이후 변수를 검토한다. |
| Colab 메모리 | 필요한 컬럼만 읽고 자료형을 줄이며 중간 결과를 Parquet으로 저장한다. |
| 과적합 | 고정 분할, 교차검증과 제한된 튜닝을 사용하고 테스트 세트를 봉인한다. |
| 확률 왜곡 | Calibration Curve와 Brier Score를 확인하고 필요할 때 확률을 보정한다. |
| 데이터 한계 | 해외 과거 공개 데이터 기반의 교육용 프로토타입임을 명시한다. |
| 공정성·오용 | 주요 하위그룹 성능을 점검하고 자동 신용판단에 사용하지 않는다. |
| 정보 유출 | 모든 금융 데이터, 모델 산출물, 환경변수와 인증정보를 Git에서 제외한다. |

## 10. 형상관리와 개발 원칙

- 한 번에 전체 프로젝트를 구현하지 않고 Stage 단위로 진행한다.
- 각 Stage 시작 전 입력, 산출물과 완료 조건을 확인한다.
- 원본 데이터는 변경하지 않으며 중간·가공 데이터도 Git에 올리지 않는다.
- 모델과 전처리 직렬화 파일은 크기와 관계없이 Git에 올리지 않는다.
- 코드, 설정, 문서처럼 결과를 재현하는 데 필요한 파일만 버전 관리한다.
- 데이터 검증, 전처리, 모델링, 서비스처럼 의미 있는 작업 단위로 커밋한다.
- random seed, 데이터 버전, 실행 설정과 실제 평가 결과를 함께 기록한다.
- 모델링 전에 데이터 구조, 결측, 중복과 누수 가능성을 확인한다.
- 기존 코드를 임의로 삭제하거나 근거 없이 성능 수치를 작성하지 않는다.
