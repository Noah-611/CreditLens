# CreditLens 프로젝트 계획서

> 대출 신청·외부 신용·과거 상환 데이터를 분석하고 여러 머신러닝·딥러닝 모델을 학습·비교하여 상환곤란 위험을 분류하는 주 1회·총 7회차(약 7~8주) 데이터분석·AI 프로젝트

## 0. 제1목표: 과제 제출용 주제 선정

이 프로젝트의 제1목표는 주 1회씩 진행하는 총 7회차(약 7~8주) 동안 데이터 확보·정제·EDA, 고객 단위 피처 구축, 모델 학습·튜닝·평가, 설명 가능성 분석과 최소 시연 프로그램을 완성하는 것이다. NICE평가정보 데이터서비스운영 직무에 맞춘 SQL, 데이터 품질, 입출력 명세와 모니터링은 분석·AI 결과의 신뢰성을 보여주는 부목표로 둔다.

### (1) 프로젝트 팀 및 주제

- **팀명:** CreditLens Lab
- **프로젝트 이름:** CreditLens - 대출 상환위험 분석 및 우선심사 지원 서비스
- **한 줄 정의:** 대출 신청·외부 신용·과거 상환 데이터를 활용하여 대출 신청자의 상환곤란 위험을 분류하고 확률을 추정하는 모델

### (2) 문제 정의 및 목표

- **해결하고자 하는 문제점:** 금융기관이 모든 대출 신청자를 동일한 수준으로 상세 심사하기에는 많은 시간과 인력이 필요하다. 또한 상환곤란 고객은 전체 고객 중 소수이기 때문에 단순한 기준만으로 위험고객을 효율적으로 선별하기 어렵다.
- **머신러닝의 역할:** 과거 대출 신청정보, 외부 신용거래와 납부기록을 학습하여 보류한 고객 데이터에서 신규 신청 상황을 모사하고, 상환곤란 확률과 우선검토 대상을 추정한다.
- **최종 결과물:** 고객의 신청정보와 고객 단위로 집계한 신용거래·납부정보를 입력하면 상환곤란 확률, 모델 위험등급, 주요 위험요인과 우선검토 시뮬레이션 결과를 제공하는 Streamlit 프로그램을 구현한다. 같은 추론 기능을 FastAPI REST API로도 제공해 외부 시스템이 연동할 수 있는 인터페이스를 로컬에서 시연한다.

우선검토 결과는 validation에서 정한 cutoff를 적용한 교육용 시뮬레이션이며, 실제 대출 승인·거절이나 공식 신용등급을 자동 결정하지 않는다.

### (3) 데이터 확보 계획

- **데이터 소스:** [Kaggle Home Credit Default Risk](https://www.kaggle.com/competitions/home-credit-default-risk/data)
- **데이터 구성:** `application_train.csv`의 대출 신청정보, `bureau.csv`의 외부 금융기관 신용거래, `installments_payments.csv`의 과거 납부기록을 사용한다. 소득, 대출금액, 연간 상환액, 나이, 재직기간, 외부 신용평가값, 과거 대출 수·잔액, 지연납부 비율, 평균·최대 지연일과 미납금액을 분석하고 비율·집계 파생변수를 만든다.
- **예상되는 이슈:** 약 8%인 상환곤란 클래스의 불균형, 결측치, 고객당 여러 거래로 인한 중복 조인, 약 1,360만 건 납부기록의 메모리 사용, 예측 시점 이후 정보에 의한 누수와 해외 과거 데이터라는 한계가 있다.

### (4) 기술 스택과 역할

- **사용 도구:** Python, WSL2 Ubuntu, VS Code/PyCharm, Google Colab, Pandas, NumPy, DuckDB SQL, PyArrow, Matplotlib, Seaborn, Scikit-learn, LightGBM, TensorFlow, SHAP, Streamlit, FastAPI, Pytest, Git, GitHub
- **역할:** 개인 프로젝트로 데이터 확보·구조 분석, 정제, 고객 단위 데이터셋 구축, 금융 파생변수 설계, EDA, 머신러닝·딥러닝 모델 학습 및 평가, SHAP 분석, Streamlit 프로그램과 FastAPI 예측 API 구현을 담당한다.

사전학습 모델을 가져오는 프로젝트가 아니므로 `파인튜닝`이 아니라 표 형태 금융 데이터로 Logistic Regression, Random Forest, LightGBM과 TensorFlow MLP를 직접 **학습하고 하이퍼파라미터를 튜닝**한다.

과제 양식의 `1일차~7일차`는 실제 진행 기준으로 `1회차~7회차`를 의미하며, 수업은 주 1회 진행되어 전체 기간은 약 7~8주다.

## 2. 문제 정의와 프로젝트 범위

### 해결하려는 문제

금융기관이 모든 대출 신청자를 동일한 깊이로 심사하려면 많은 시간과 인력이 필요하다. 또한 상환곤란 고객은 전체 고객 중 소수이므로 단순 규칙이나 정확도만으로는 위험고객을 효과적으로 찾기 어렵다.

### 머신러닝의 역할

과거 대출 신청정보, 외부 신용거래와 납부기록을 학습하여 보류한 고객 데이터에서 신규 신청 상황을 모사하고, 상환곤란 위험점수·보정 확률과 주요 위험요인을 분석한다.

### 포함 범위

- 신용정보의 구조·품질·분포와 TARGET 관계 분석
- Python·SQL 기반 고객 단위 분석 데이터 마트 구축
- 고객별 상환곤란 위험점수와 확률 보정 후 확률
- 저·중·고 모델 위험구간 제공
- 고객별 주요 위험요인 설명
- 심사 가능 인원을 고려한 우선검토 Top-K·cutoff 시나리오
- 데이터 버전과 모델별 성능 비교
- 데이터·모델 품질과 분포 변화의 모니터링 기준 설계
- 분석 결과 활용을 위한 입력·출력 요건
- 고정된 최종 모델을 사용하는 최소 Streamlit 프로그램과 FastAPI 예측 API

### 제외 범위

- 대출 자동 승인·거절 또는 실제 신용 의사결정
- 실제 개인신용정보의 수집·처리
- 실서비스 수준의 보안·규제 인증 및 운영 배포
- 분석·모델링보다 앞선 대규모 웹서비스·클라우드 인프라 구현
- 핵심 결과와 업무 근거 없이 모델 수만 늘리는 딥러닝 실험

### AI 활용 원칙

CreditLens는 데이터 분석과 신용위험 모델 개발을 학습하기 위한 프로젝트다. 모델 결과만으로 대출을 승인하거나 거절하지 않으며, 위험점수·보정 확률과 모델 위험구간은 검토 순서를 정하기 위한 참고 정보로만 사용한다.

- 데이터 구축부터 최종 추론까지 동일한 피처 정의와 데이터 계약을 재사용한다.
- 분석 결과를 지표, 그래프와 Markdown 보고서로 논리적으로 설명한다.
- 성능 수치와 분석 결과는 실제 실행 결과만 기록한다.
- 원본·중간·가공 금융 데이터와 학습 모델 파일, 인증정보가 Git에 포함되지 않는다.

구체적인 목표 성능은 데이터를 확인하기 전에 임의로 정하지 않는다. Stage 4 기준 모델 결과를 측정한 뒤 개선 목표와 최종 선정 기준을 확정한다.

3. `bureau.csv`를 고객 단위로 집계해 외부 신용거래 건수, 활성 대출, 잔액, 연체와 최근성 피처를 추가한 V2를 만든다.
4. `installments_payments.csv`를 고객 단위로 집계해 납부 지연 횟수·비율, 지연일과 납부금액 비율 등의 행동 피처를 추가한 V3를 만든다.
5. Python이 실행 흐름과 검증을 담당하고, 대용량 조회·집계는 DuckDB SQL과 Parquet을 활용해 처리시간과 메모리 사용량을 기록한다.
6. 고객 수, 키 유일성, 조인 전후 행 수, `TARGET`과 split 보존을 자동 검증한다.
7. 주요 SQL 집계 결과와 Python 검산 결과가 일치하는지 합성 데이터로 대사한다.
8. 피처명, 산식, 원천 테이블, 결측 의미와 예측 시점 사용 가능 여부를 Markdown 피처 사전에 기록한다.
9. 입력 checksum, 데이터 버전, 행·열 수와 실행 설정을 분석 마트 빌드 명세에 기록한다.
10. V2·V3 신규 피처의 분포 분석과 처리 결정은 train에서만 수행하고 validation·test는 스키마·키·행 수 검증에만 사용한다.

**산출물**

- 재현 가능한 Python·SQL 피처 생성 코드
- V1·V2·V3 Parquet 파일(로컬 전용)

- Markdown 피처 사전
- 데이터 품질·SQL/Python 대사 보고서와 집계 테스트

**완료 조건**

### Stage 4. 전처리·평가 체계와 기준 머신러닝 모델 구축

**목표**

향후 모델과 데이터 버전을 공정하게 비교할 재현 가능한 기준선과 신용위험 평가 체계를 만든다.

**구현 단계**

1. 결측 대치와 범주 인코딩을 포함한 전처리 파이프라인을 train에만 `fit`한다.
2. Dummy Classifier로 클래스 불균형을 반영한 최저 기준을 측정한다.
3. V1·V2·V3로 해석 가능한 Logistic Regression 기준 모델을 학습한다.
4. V3로 제한된 깊이·트리 수와 `class_weight`를 사용한 Random Forest 비교 모델을 학습한다.
5. ROC-AUC, PR-AUC, KS, Gini, Brier Score와 Recall·Precision·Lift@Top-K를 공통 평가 함수로 구현한다.
6. ROC·PR·Calibration Curve와 위험도 decile별 고객 수·상환곤란 비율·누적 포착률을 생성한다.
7. 심사 가능 인원을 가정한 Top-K 시나리오는 validation에서만 비교한다.
8. 데이터 버전, seed, 피처 목록, 전처리 설정, 실행시간과 결과를 실험 기록에 남긴다.
9. 핵심 지표와 전처리 누수 방지 조건을 자동 테스트한다.

**산출물**

- Logistic Regression·Random Forest 학습 파이프라인
- 공통 평가 모듈과 기준 모델 분석 보고서
- 재현 가능한 실험 설정

**완료 조건**

- 동일 분할에서 기준 모델 지표를 재현할 수 있다.
- 지표 단위 테스트와 수기 검산 결과가 일치한다.
- 이후 모델이 같은 평가 인터페이스를 사용할 수 있다.
- 테스트 세트는 사용되지 않는다.

### Stage 5. LightGBM·TensorFlow MLP와 데이터·모델 비교

**목표**

외부 신용정보와 납부이력의 추가 가치 및 전통적 머신러닝·딥러닝 모델의 차이를 분석하고 최종 후보를 선정한다.

**구현 단계**

1. LightGBM을 동일한 분할과 평가 인터페이스에서 학습한다.
2. Logistic Regression과 LightGBM의 V1·V2·V3 성능을 비교해 각 정보 원천의 추가 가치를 측정한다.
3. V3로 수치 스케일링, 범주 인코딩, `class_weight`와 early stopping을 적용한 TensorFlow MLP를 처음부터 학습한다.
4. V3에서 Logistic Regression·Random Forest·LightGBM·TensorFlow MLP를 같은 지표로 비교한다.
5. 신청정보·외부 신용이력·납부행동 피처군별 ablation 분석을 수행한다.
6. 제한된 하이퍼파라미터 탐색은 train 내부 교차검증으로 수행하며 각 fold의 전처리도 해당 학습 부분에만 `fit`한다.
7. MLP의 early stopping용 데이터도 train 내부에서 분리하고 validation을 신경망 학습에 사용하지 않는다.
8. 확률 보정은 train 내부 OOF 예측 또는 내부 calibration split으로 수행하고 validation에는 보정기를 `fit`하지 않는다.
9. 성능뿐 아니라 안정성, 설명 가능성, 학습·추론 비용을 함께 비교한다.
10. validation은 데이터 버전·후보 모델의 성능과 Top-K 잠정 시나리오 비교에만 사용하고, 그 결과로 최종 설정을 고정한다.
11. 채택·기각한 실험과 그 이유를 의사결정 기록에 남긴다.

**산출물**

- 모델·데이터 버전별 비교표와 TensorFlow 학습 이력
- 데이터 원천 추가 가치와 피처군 ablation 분석
- 튜닝·확률보정 실험 및 의사결정 기록
- 최종 모델 후보와 선정 근거

**완료 조건**

- 모든 후보가 같은 분할과 지표로 평가된다.
- 데이터 버전 추가 효과와 모델 복잡도 효과를 구분해 설명할 수 있다.
- 테스트 세트는 아직 최종 선택에 사용되지 않는다.

### Stage 6. 최종 모델 해석·위험전략·설정 고정

**목표**

최종 모델의 예측 근거와 활용 기준을 validation에서 분석하고, 7회차 봉인 테스트 전에 모든 설정과 cutoff를 고정한다.

**구현 단계**

1. Stage 5에서 선택한 데이터·전처리·모델 설정을 최종 고정한다.
2. 최종 모델에 맞는 SHAP explainer로 전역 중요도와 고객별 주요 위험요인을 계산한다. MLP가 최종 모델이면 계산비용과 explainer 호환성을 먼저 검증한다.
3. 고객별 설명을 사람이 확인할 수 있는 주요 위험요인 문구로 매핑하되 인과관계로 표현하지 않는다.
4. validation에서 위험도 decile과 저·중·고 모델 위험구간을 정의한다.
5. 심사 가능 인원별 Top-K 포착률과 cutoff 시나리오를 비교해 최종 활용 기준을 확정한다.
6. 금융이력 부족자와 주요 하위그룹의 성능·오류·확률보정 차이를 점검한다.
7. 데이터·전처리·모델·확률보정·cutoff 설정과 산출물 checksum을 고정하고 테스트 세트는 계속 봉인한다.
8. 데이터 한계, 오용 위험과 사람의 최종판단 원칙을 모델 카드에 기록한다.

**산출물**

- validation 최종 성능표와 고정된 모델 설정
- SHAP 설명 결과
- 모델 위험구간·우선검토 시나리오
- 최종 모델 개발 보고서와 모델 카드

**완료 조건**

- 최종 선택과 임계값의 근거가 검증 데이터 결과로 설명된다.
- 테스트 세트는 Stage 8의 최종 평가 전까지 사용되지 않는다.
- 모델의 한계와 사용 금지 범위가 문서화되어 있다.
- 결과가 공식 신용등급이나 자동 승인·거절 기준이 아님을 명시한다.

### Stage 7. Streamlit·FastAPI 예측 프로그램과 데이터서비스 요건

**목표**

고정된 모델을 공통 추론 파이프라인으로 제공하는 최소 Streamlit 프로그램과 FastAPI REST API를 구현하고, 입력 검수와 데이터·모델 모니터링 요건을 정의한다. 이 단계는 분석 결과를 보여주는 프로토타입이며 프로젝트의 본체는 Stage 3~6의 분석·AI다.

**구현 단계**

1. 분석가·심사 담당자·데이터서비스 운영자를 사용자로 정의하고 결과 이용 시나리오를 정리한다.
2. 모델이 실제로 사용하는 전체 피처 레코드의 항목, 자료형, 필수 여부, 허용 범위와 데이터·모델 버전을 입력 계약으로 정의한다.

4. 전처리와 모델 추론을 한 함수로 묶어 Streamlit, FastAPI와 배치 스코어링 CLI가 같은 코드를 재사용하게 한다.
5. FastAPI에 `/health`와 `/predict` 엔드포인트를 만들고 Pydantic으로 입력 스키마와 오류 응답을 검증한다.
6. 상환곤란 보정 확률, 모델 위험등급, 주요 위험요인과 validation cutoff 기반 우선검토 시뮬레이션 값을 반환한다.
7. 정상·결측·범위 오류·미등록 코드·스키마 변경과 같은 입력에 같은 결과가 나오는지 자동 테스트한다.
8. 처리 건수, 오류 건수, 결측률, 피처·점수 분포와 PSI·CSI 변화 시나리오를 점검한다.
9. 정답이 나중에 확보되는 상황의 ROC-AUC, PR-AUC, KS, calibration과 위험구간별 상환곤란 비율 모니터링 기준을 정의한다.
10. 데이터·모델 버전 변경, 실패 확인과 재처리 절차를 짧은 Markdown Runbook으로 작성한다.

**산출물**

- FastAPI `/health`·`/predict` REST API
- 데이터서비스 요구사항과 입력·출력 데이터 계약
- 재현 가능한 배치 스코어링 인터페이스
- 인수 검수 시나리오와 자동 테스트
- 데이터·모델 모니터링 계획
- 운영 Runbook

**완료 조건**

- Git 추적 파일에 데이터, 모델, 비밀정보가 없다.

### Optional Extension. 7회차 이후 포트폴리오 고도화

Stage 0~8의 7회차 결과가 완성된 뒤 WOE/IV Scorecard, Docker와 AWS 참조 아키텍처를 검토한다. AWS는 S3 입력, 배치 스코어링, 모델 산출물 관리와 CloudWatch 모니터링 흐름을 설명하는 수준을 우선하며 실제 배포가 분석보다 앞서지 않게 한다. 추가 모델은 명확한 분석 가설과 비교 가치가 있을 때만 별도 실험한다.

## 8. 예상 이슈와 대응

| 이슈 | 대응 |

## 10. 형상관리와 개발 원칙

- 한 번에 전체 프로젝트를 구현하지 않고 Stage 단위로 진행한다.
- 각 Stage 시작 전 입력, 산출물과 완료 조건을 확인한다.
- 원본 데이터는 변경하지 않으며 중간·가공 데이터도 Git에 올리지 않는다.
- 모델과 전처리 직렬화 파일은 크기와 관계없이 Git에 올리지 않는다.
- 코드, 설정, 문서처럼 결과를 재현하는 데 필요한 파일만 버전 관리한다.
- 데이터 검증, 분석 마트, 모델링, 해석·모니터링처럼 의미 있는 작업 단위로 커밋한다.
- random seed, 데이터 버전, 실행 설정과 실제 평가 결과를 함께 기록한다.
- 모델링 전에 데이터 구조, 결측, 중복과 누수 가능성을 확인한다.
- 기존 코드를 임의로 삭제하거나 근거 없이 성능 수치를 작성하지 않는다.
